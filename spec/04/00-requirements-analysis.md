# 04 - 需求分析与边界澄清

## 1. 目标重述

本阶段目标是在当前 `star-agent` 项目中新增“多 Agent 交流室（Multi-Agent Room）”，满足以下核心特征：

1. 多角色 Agent 共享同一份会话消息，不再各自维护私有历史。
2. 共享范围仅限“非思考内容”（不共享 reasoning / chain-of-thought）。
3. 角色发言必须串行（严格一人一轮），禁止并行发言。
4. 存在一个“编剧 Agent（Playwright）”负责全局叙事控制。
5. 角色累计发言 100 次后，编剧介入一次，读取共享消息并重写世界观与角色人格提示词，然后继续串行对话。
6. UI 需明显体现“编剧掌控全局”，并展示所有角色与编剧的系统提示词（当前允许编辑）。
7. UI 需以聊天形式展示多角色对话，消息使用角色名称而非统一 assistant。

## 2. 与现有架构的关键差异

当前实现（基于 `src/app/api/chat/route.ts`）是“单聊天请求 -> 选一个 agentId -> 返回一条主 assistant 流”。

已有的多 Agent 能力（`master` + `sub-agent`）本质是：

1. 主 Agent 发起工具调用创建子任务。
2. 子 Agent 独立执行并回传流事件。
3. 主 Agent 在编排循环中恢复。

这与“多角色共享一个会话池并轮流说话”的业务语义不同，不能直接复用为交流室主干。

## 3. 需求细化（工程可执行）

## 3.1 “共享消息”定义

建议定义 `SharedMessage` 作为交流室的唯一事实来源（single source of truth）：

1. 共享用户输入。
2. 共享角色可见输出（普通文本、可见工具结果摘要）。
3. 不共享 reasoning 类型内容。
4. 消息按全局时序存储，任何角色生成下一轮时都读取同一上下文窗口。

## 3.2 “非思考内容”执行定义

建议采用白名单规则构建“可共享上下文”：

1. `text` part：可共享。
2. 工具输出：仅共享用户可见摘要，不共享内部推理。
3. `reasoning` part：禁止入库、禁止广播给其他角色。

说明：前端可继续渲染本轮模型返回的 reasoning（如果你希望可折叠查看），但它不进入共享池。

## 3.3 “100 次后编剧介入”定义

建议把“角色对话总计 100 次”明确为：

1. 仅统计角色 Agent 的 assistant 发言。
2. 不统计用户消息。
3. 不统计编剧消息。
4. 达到 100 后触发一次 `playwright-review` 阶段，完成后计数归零并进入下一周期。

## 4. 方向性决策（需要确认）

为避免后续返工，建议采用以下方向：

1. 新建“交流室专用运行时”而不是复用现有 `master/sub-agent` 编排循环。
2. 新建交流室数据模型（room/participant/sharedMessage/promptRevision），不挤入现有 `conversation/messages` 简表。
3. 在 UI 上为交流室做独立页面或独立模式，而非在现有单 agent chat 页面中硬塞状态机。

这是本方案的基础假设，后续所有实施文档都按该方向展开。
